The tour

What you write, and what comes back

Every feature, one at a time, each with a scenario in and a captured result out. Nothing here is mocked: each box is a file under assets/homepage, stamped with the commit and the command that produced it. Every example is a small project that scripts/homepage/capture.sh runs at each regeneration, and the boxes are its output — so the tour proves each claim as of the last capture. The front page is the short version.

The refusal: compile errors, before a browser opens

A scenario is four lines of Gherkin. :user/alice is a declared subject and an instance — a keyword naming the subject’s type and the instance, declared in the glossary. Login.submit is an intent reference: an intent is a named thing on a page, with the elements it owns, declared as a small data file. Here the actor is misspelled on the first step and the element on the third:

Every step resolves to who, does what, to which thing, through which interface, before the run. A word that does not resolve stops the run with a suggestion and the file and line where the right name is declared. Exit 2: nothing ran, no browser opened. This is the fifteen seconds that follow:

A typo is the fastest case to see, not the important one. The important ones are a glossary entry renamed and left dangling across forty scenarios; a merge that leaves references pointing at nothing; a step library refactored underneath a suite nobody re-ran. Each is the same failure to resolve, caught the same way, at the same moment: before a browser opens.

How strict, exactly: unknown subjects and unknown interfaces block; unknown verbs warn; unknown intent references are errors; raw locators in step text are off by default; untyped step definitions warn. Each is configurable. Strictness follows ownership: whoever owns the word decides how hard the check is.

The failure row

Four steps against a shopping cart. Three pass. The fourth is what a failure looks like here:

  • Which actor, which thing, which step. :user/shopper, looking at Cart.items[-1].status — the status of the last cart row — on the fourth step. Not a selector timeout.
  • What it expected and what it saw. 'removed' against 'in cart', inside a three-second deadline. The deadline, the interval and the poll count are printed, so nobody has to guess whether it waited long enough.
  • The screenshot and the browser console, attached at the instant of failure. The console line names the app’s bug: the click landed on item 3, and the app marked Apples removed. The console attaches on the WebDriver backend.

The same failure reaches your CI two more ways — the JUnit case the pipeline widget reads, and the machine-readable record a script reads. One failure, one set of attachments:

Page objects are data, addressed by path

Cart.items[-1].remove is the remove button on the last cart row: a collection, a negative index, an element. Cart.items[*].price fans out to every row, so should see 3 … elements is a count of all members. Thread.post[1].comment[-1].author walks two levels of nesting with an index at each. The objects are two small data files; the locators live there and nowhere else, so when the page moves you edit one binding and zero scenarios.

How a name finds an element

Two actors, two browsers, and costumes

alice and bob are two instances of one declared subject. Each gets its own browser; nothing is shared unless you say so. The glossary shows the declaration and that the project uses it fourteen times.

Subjects are types, with instances, for three reasons. Every line says who is acting and in what context — not I, not the user, not a convention kept in a wiki — so “why is the admin in this scenario?” is answered by the line itself. A browser per instance costs nothing: name a second instance and its session exists, with no context to create and thread through the test body; an environment, or a costume, is assigned to the instance once. And because they are types, the same scenario can later run as someone else and the answers compared — derived denials, under Not yet.

A costume is a named browser identity an actor wears — a profile, a locale, sometimes an already-signed-in session — declared once, reused, with custody rules. This project has none; the command says how to make one. Costumes are a WebDriver-backend feature today.

The parser never needs step definitions

Compatibility is a decision, stated exactly. The parser accepts every legal Gherkin file: 50 of 50 official Cucumber files parse and 12 of 12 invalid ones are rejected. sl fmt formats a suite losslessly with no step definitions and no config:

The compiler, by choice, runs only typed steps: strictness over compatibility. An existing step library does not run here; feature files and page objects migrate. A plain Cucumber suite parses, every keyword, and nothing runs, because nothing in it is typed yet — and it says so, counts what it saw, and names the next command. Unshifted in that output means untyped; shifted means typed.

An agent-led migration skill is next. Until then the on-ramp is what you see above: parse everything, run nothing, say what typing means.

The browser backend is one line of config

ShiftLefter sits between your scenarios and the browser driver and does not care which driver it is. WebDriver is the default and bundled. Switching to Playwright is one line of config and one dependency:

The step contract is the same on both: a feature file that runs on one runs on the other, with the same vocabulary, the same planning errors, and the same nested addressing. The two backends do differ — console capture and costumes are WebDriver-only today — and the differences are kept in one table rather than smoothed over.
