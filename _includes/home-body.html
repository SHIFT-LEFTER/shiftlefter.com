A failure, as it arrives

Four steps against a shopping cart. Three pass. The fourth is what a failure looks like here — and the only thing on this page that was written by hand is the scenario.

  • Which actor, which thing, which step. :user/shopper, looking at Cart.items[-1].status — the status of the last cart row — on the fourth step. Not a selector timeout.
  • What it expected and what it saw. 'removed' against 'in cart', after 26 polls inside a three-second deadline. The deadline, the interval, and the poll count are printed, so nobody has to guess whether it waited long enough.
  • The screenshot and the browser console, attached at the instant of failure. The console line names the app's bug for you: the click landed on item 3, and the app marked Apples removed.

Rarity: screenshots on failure are common; the assembled row — actor, intent, step, poll count, console — is uncommon. The console attaches on the WebDriver backend today.

Open the real report — one file, no server, failures expanded. A bigger one, 41 scenarios with every outcome in it, is at /report/.

Underneath is a Gherkin runner: Cucumber's Gherkin, every keyword, 50 of 50 official files; real browsers and SMS; JUnit XML and HTML for CI. That is the floor, not the pitch. The pitch is what it refuses to do.

What do I write?

Gherkin. The step is where it differs. In Cucumber a step is a regular expression over a string: whatever matches, runs. Here a step is a sentence — subject, verb, object — and every word has to resolve against a glossary you own before anything runs.

A step is a sentence, not a regex

Every step resolves to who, does what, to which thing, through which interface — before the run. When a word does not resolve, this is the fifteen seconds that follow:

An actor nobody declared, a verb that isn't one. Both caught, both with a suggestion; the actor's suggestion comes with the file and line where the right name is declared; the run exits 2 — nothing ran, no browser opened. That move — resolve every word before executing any — is the whole product. We call it compiling behavior. Everything below is what it buys.

Rarity: rare as a system.

The code arrives by SMS. The pattern names it code. The next step types {code} into a browser field. No glue code, no fixture, no shared variable — a value captured in one step is a word in the next, across interfaces.

Two actors, two browsers, no setup

alice and bob are two instances of one declared subject. Each gets its own browser; nothing is shared unless you say so. The glossary shows the declaration, and that the project uses it fourteen times.

A costume is a named browser identity an actor wears — profile, locale, sometimes an already-signed-in session — declared once, reused, with custody rules. This project has none; the command says how to make one. Where a costume lives on disk and what it persists: Costumes.

Rarity: uncommon. Costumes: common-to-uncommon — most frameworks accept a custom profile; ours is a named, wearable artifact with custody.

What are you promising me?

Five sentences you can check. Each one is proved by something on this page.

Never guess before the run.

Every step binds and every word checks before a browser opens. A failure to bind names the fix and the file and line where the right thing is declared.

Never lie after it.

A green is a measurement. A run that could not measure says so in its exit code — never in a green.

Byte-identical under parallelism.

--max-parallel 4, and the report is the same as the sequential run — in content and in order.

Rarity: uncommon — parallel is common; byte-identical output is rare.

Two passes, forever.

The parser never needs step definitions. sl fmt on a suite with no step definitions and no config, formatted losslessly; 50 of 50 official Cucumber files parse and 12 of 12 invalid ones are rejected.

Your Gherkin stays Gherkin.

A plain Cucumber suite parses, every keyword. Nothing runs, because nothing in it is typed yet — and it says so, counts what it saw, and names the next command. Compatibility is the floor. The step body is where this is stricter.

How strict, exactly.

Unknown subjects and unknown interfaces block. Unknown verbs warn. Unknown objects and raw locators are off by default. Untyped step definitions warn. Each is configurable. Strictness follows ownership: who owns the word decides how hard the check is.

The vocabulary rule

Where it is, honestly

Solid today

  • The failure report — actor, intent, step, screenshot, console; HTML, JUnit XML, machine-readable.
  • Typed steps refused before the run, with suggestions and the declaring file and line.
  • A data plane — a value captured in one step is a word in the next, across web and SMS.
  • Page objects as data, addressed by path, indexed, negative indexes included.
  • Multi-actor browser driving — isolated sessions; costumes for durable identities.
  • The dry-run plan and the exit-code contract.
  • Parallel scenarios with identical output; tag selection; JUnit XML, HTML, and machine-readable output.
  • Gherkin parsing and lossless formatting — 50 of 50 official files, usable as a CI gate.
  • The documentation inside the jar, and an on-ramp for a suite that has never been typed.

Not yet

  • The traceability graph — requirements to use cases to features to the runs that prove them. Its inputs exist (below); the graph does not.
  • Semantic diffing of live pages — a developer preview at the REPL today, not a command.
  • Brownfield migration — there is an on-ramp (it parses your suite, runs nothing, and says what shifting means), not a converter.
  • Browser-console capture on the Playwright backend — the WebDriver backend only, today.
  • Derived denials — what your app must refuse, derived from the glossary. Designed, not shipped.

One author, with agents in the loop; the agent surface is used on itself. Adopt it for the left column. The right column is why the discipline compounds: the same vocabulary that refuses a typo today is what the graph will read.
